# Glossário de negócio — Renovi

Termos extraídos ou inferidos a partir de nomes de entidades, rotas e interface. Quando o significado operacional não está explícito no código, está sinalizado.

| Termo | Significado na Renovi | Onde aparece (exemplos) |
|-------|------------------------|-------------------------|
| **Pedido / solicitação de serviço** | Registro de pedido de orçamento do cliente, com serviço, dados do formulário, fotos e localização. | Tabela `service_requests`; rota “Meus Serviços” no menu cliente (`dashboardMenu.ts`). |
| **Service request** | Nome técnico em inglês do mesmo conceito. | Código, APIs, migrations. |
| **Orçamento (UI cliente)** | Propostas recebidas por pedido: sheet **Comparar orçamentos** / **Histórico de orçamentos** em Meus Serviços; negociação ativa em Conversas. | `my-services` + `negotiation-proposals`; `/dashboard/services`; `/dashboard/chats`. |
| **Orçamento (UI prestador)** | Propostas enviadas e negociação ativa. | `/dashboard/chats`; acompanhamento por pedido via `/dashboard/services` + `view-services` (`list_services`, fase `negotiation`). |
| **Proposta** | Oferta formal do prestador para um pedido: valores, impostos/taxa da plataforma, prazo, janelas sugeridas, status. | `provider_proposals`, RPCs `create_provider_proposal`, etc. |
| **Trabalho / Job** | Na UI do prestador, oportunidade com **visibilidade** concedida pelo matching (lote ou mercado aberto). | `provider-jobs`, RPC `list_provider_opportunities`, Edge `list-provider-opportunities`. |
| **Matching progressivo** | Distribuição de pedidos OPEN em **lotes** ao longo do tempo, com notificações e gates (pausa, parada, expiração). Pedidos **sem nenhuma proposta**: push aos 24h; auto-cancel + push/e-mail aos 48h. | `service_request_dispatches`, cron `matching_process_service_request_dispatches`, cron `process_service_requests_without_proposals`; [matching-dispatch](./modulos/matching-dispatch/README.md). |
| **Dispatch lote** | Abertura de um lote de prestadores elegíveis (discovery + ranking) em um ciclo do cron: grava batch, **visibilidade** `source=batch` e dispara notificação MMD `matching.new_opportunity`. | `matching_open_batch`; [dispatch-e-visibilidade](./modulos/matching-dispatch/features/dispatch-e-visibilidade.md). |
| **Visibilidade (batch)** | Registro que autoriza um prestador a ver um pedido no feed com origem **lote**. | `service_request_provider_visibility` (`source = batch`). |
| **Mercado aberto (fallback)** | Após esgotar lotes, pedido visível a prestadores elegíveis por bairro/serviço sem ter estado em lote. | `source = fallback`, badge *Mercado aberto*; `fallback_opened_at`. |
| **`fallback_dismiss`** | Registro de dispensa do prestador no feed de **mercado aberto** (não é a coluna `source` do feed). Remove do feed sem bloquear `get_service` nem CNS. | Tabela/linha `fallback_dismiss`; evento `provider_declined`; matching-dispatch. |
| **Lifecycle do dispatch (24h / 48h)** | Duas janelas do matching: (1) **lifecycle do dispatch** — default **48h** desde `created_at` → `DISPATCH_EXPIRED`; (2) pedido **sem nenhuma proposta** — push aos **24h** (`matching.no_proposal_seeking`) e auto-cancel + push/e-mail aos **48h** (`matching.no_proposal_auto_cancelled`). Qualquer linha em `provider_proposals` exclui o pedido do janitor 24/48. | Constantes `matching.dispatch_lifecycle_hours`, crons de matching; [dispatch-e-visibilidade](./modulos/matching-dispatch/features/dispatch-e-visibilidade.md). |
| **Dispatch de pedido** | Ciclo de vida da distribuição de um pedido (≠ Message Dispatcher / MMD). | `service_request_dispatches`, doc [matching-dispatch](./modulos/matching-dispatch/README.md). |
| **Lease (matching)** | Trava CAS para um worker processar um dispatch sem concorrência; leases órfãos liberados pelo janitor `matching_force_release_stale_leases`. | Cron matching; [dispatch-e-visibilidade](./modulos/matching-dispatch/features/dispatch-e-visibilidade.md). |
| **Beacon de dispositivo** | Registro por instalação de push (token FCM) + metadados do aparelho; para prestador, também **localização operacional**. Upsert em conflito `(profile_id, device_id)`. | `user_device_beacons`, `DeviceBeaconProvider`; [device-beacon](./modulos/device-beacon/README.md). |
| **Localização operacional** | Coordenadas aproximadas do prestador sincronizadas no beacon (baixa frequência; debounce 60s; filtro 350 m no nativo). Distinta do GPS de foreground usado só no sort “Mais próximos” do feed. | `device-beacon`; [rastreamento-dispositivo](./modulos/device-beacon/features/rastreamento-dispositivo.md). |
| **Explainer de localização** | Dialog in-app (pt-BR) antes do prompt do SO: matching “~20 km”, coleta periódica; no nativo, tracking em background com notificação persistente. Máximo uma vez por instalação (`orbit.location_prompt_seen`). | `LocationPermissionDialog*`; Preferences `orbit.location_prompt_*`. |
| **Freshness (beacon)** | Beacon elegível para discovery só se `location_recorded_at` estiver dentro de `matching.beacon_location_max_age_hours` (seed **24**). Fora da janela, a linha some de `provider_latest_locations`. | Trigger `matching_refresh_provider_latest_location`; matching. |
| **H3 (resolução 7)** | Índice espacial H3 no cliente (path supabase-js) com resolução **7**, alinhada a `matching.h3_resolution`; discovery usa H3 + raio. Path HTTP Android pode omitir `h3_index` (fallback SQL). | `matchingH3.ts`; constante `H3_RESOLUTION_MATCHING`. |
| **Localização latest (prestador)** | Agregado derivado do beacon fresco, usado na discovery de lotes. | `provider_latest_locations`. |
| **Calendário do prestador** | Agenda **somente leitura** dos serviços contratados do prestador (lista por dia no mobile; grade mensal no desktop ≥768px). Entrada via banner em Meus Serviços; **sem** item de menu. | `/dashboard/services/calendar`; feature `provider-calendar`; [calendario-do-prestador](./modulos/provider-calendar/features/calendario-do-prestador.md). |
| **Turno agendado** | Faixa do dia do serviço contratado: `morning`, `afternoon` ou `full_day` (`scheduled_shift`). Labels UI via `formatShift`. | `contracted_services.scheduled_shift`; calendário / detalhe. |
| **Vista lista / vista grade** | Modos do calendário do prestador (`CalendarViewMode`): `list` (&lt;768px, scroll infinito) vs `grid` (≥768px, mês). Sem toggle do usuário — só breakpoint. | `useProviderCalendarViewMode`; `provider-calendar`. |
| **Avaliação de serviço** | Nota pós-conclusão; alimenta estatísticas do prestador no ranking. | RPCs `submit_service_rating`, `update_service_rating`. |
| **Cliente** | Papel `client` em `profiles.role`. | Auth, RLS, rotas. |
| **Prestador / Profissional** | Papel `provider`. Cadastro em `/cadastro/profissional`. | Auth, perfil público, jobs, budgets. |
| **Credenciamento / KYC do prestador** | Onboarding NetCred da conta gateway do prestador (`provider_gateway_accounts.onboarding_status`). Só com status **`ACTIVE`** o prestador opera o painel e pode receber cobranças no split. | Feature `provider-kyc`; gate no `DashboardLayout`; [gate-e-acesso-operacional](./modulos/provider-kyc/features/gate-e-acesso-operacional.md); wizard [formulário-credenciamento-wizard](./modulos/provider-kyc/features/formulario-credenciamento-wizard.md). |
| **`onboarding_status` (NetCred)** | Campo FSM em `provider_gateway_accounts`: `PENDING_DOCUMENTS`, `DOCUMENTS_SUBMITTED` (com/sem `email_dispatched_at`), `UNDER_NETCRED_REVIEW`, `REJECTED`, `SUSPENDED`, `ACTIVE`. Qualquer valor ≠ `ACTIVE` (ou conta ausente) bloqueia o shell operacional. FSM permite **`REJECTED` → `DOCUMENTS_SUBMITTED`** no reenvio de documentos. | Gate `provider-kyc`; RPCs `payment_submit_provider_kyc` / activate / reject. |
| **Gate KYC / allowlist operacional** | Bloqueio do **conteúdo** operacional do prestador (slots + outlet) até `ACTIVE`, com **allowlist** `/dashboard/conta*` (`PROVIDER_KYC_ALLOWED_PATH_PREFIX`); menu completo do prestador permanece visível. | `ProviderKycGate`; [gate-e-acesso-operacional](./modulos/provider-kyc/features/gate-e-acesso-operacional.md). |
| **Wizard de credenciamento KYC** | Fluxo multi-etapas (tipo de cadastro → dados pessoais → banco → documentos → revisão) em `ProviderKycForm` / `useProviderKycWizard`. Entidade UI `CPF`/`CNPJ` mapeia para RPC `pf`/`pj`. Documento do representante sobe com chave **`legal-rep-id`**. | [formulário-credenciamento-wizard](./modulos/provider-kyc/features/formulario-credenciamento-wizard.md). |
| **Sessão de upload KYC (Option A)** | Fluxo create session → upload no storage → register path (`payment_create_provider_kyc_upload_session`, `payment_register_provider_kyc_upload_path`) antes do submit. Sessões órfãs no bucket `provider-kyc-documents` são limpas pelo janitor `payment_janitor_orphan_kyc_documents`. | `uploadKycDocument` em `provider-kyc`; tabela `provider_kyc_upload_sessions`. |
| **E-mail operacional de credenciamento NetCred** | Destino do e-mail com anexos KYC após submit (`dispatch-kyc-email`). Default **`credenciamento@renovi.com.br`**; override por env **`NETCRED_CREDENCIAMENTO_EMAIL`**. Não confundir com o e-mail da conta do prestador no wizard nem com o cadastro/auth em `/cadastro/profissional`. | Edge `dispatch-kyc-email` / `sendCredenciamentoEmail.ts`. |
| **Administrador** | Papel `admin` no banco; políticas e RPCs podem tratar admin de forma diferente. | Migrations, `database.types.ts`. **Painel admin não roteado no front analisado.** |
| **Slug** | Identificador amigável na URL do perfil público do prestador. | `provider_profiles_public.slug`, rota `/perfil/:slug`. |
| **Formulário dinâmico** | Formulário definido por schema JSON versionado na plataforma. | `platform_forms`, componentes `dynamic-form`. |
| **Serviço de plataforma** | Item do catálogo (`platform_services`) associado a um formulário e opcionalmente a prompt de IA. | `request-quote`, migrations de serviços. |
| **Descrição inteligente** | Geração assistida de texto (e metadados) via modelo de IA a partir do formulário e notas. | Edge `generate-smart-description`. |
| **Área de atuação** | Bairros em que o prestador declara atuar (`provider_service_area_neighborhoods`). | `my-account` (ex.: `ServiceAreaField.tsx`). |
| **Portfólio** | Imagens/itens exibidos no perfil público. | `provider_portfolio_items`, storage `provider-portfolio-images`. |
| **Urgência** | Campo opcional do pedido com valores `low` / `medium` / `high`. | `service_requests.urgency` (CHECK na migration). |
| **Complexidade do escopo** | Campo opcional `simple` / `medium` / `complex`. | `service_requests.scope_complexity`. |
| **Duração estimada (hint)** | Chaves como `under_1h`, `1_to_2h`, … definidas em CHECK. | `service_requests.estimated_duration_hint`. |
| **Status do pedido** | Enum `service_request_status`: `OPEN`, `COMPLETED` (aceite de proposta), `CANCELLED`. Valores legados `open` / `in_progress` / `closed` / `cancelled` foram migrados (CNS). Não confundir com **`list_phase`** nem com status de `contracted_services`. | `service_requests.status`; migration `20260701101200_migrate_service_requests_cns_status.sql`. |
| **Status da proposta** | `PENDING`, `ACCEPTED`, `REJECTED`, `REVISION_REQUESTED`, `REVISED`, `EXPIRED`, `REJECTED_AUTOMATICALLY`. | `provider_proposals.status` (enum CNS). |
| **`REJECTED_AUTOMATICALLY`** | Status de proposta rejeitada automaticamente (ex.: expiração / regras do CNS); na UI do prestador entra no mesmo alerta de rejeição que `REJECTED`. | Enum `provider_proposals`; `getProposalStatusLabel`; [trabalhos-e-propostas](./modulos/provider-jobs/features/trabalhos-e-propostas.md). |
| **Unidade de duração da proposta** | `hours` ou `days`. Serviço de um único dia deve usar `hours` (`days` exige valor ≥ 2). | `provider_proposals.proposal_duration_unit`. |
| **Duração do serviço contratado** | Cópia da duração da proposta aceita no contrato (`hours`/`days` + valor). Define se o reagendamento pede data única ou período. | `contracted_services.duration_unit`, `duration_value`; snapshot de reagendamento. |
| **Solicitação de reagendamento** | Pedido formal para negociar nova data/período de execução de serviço contratado; não altera a data oficial até o aceite do cliente. Cliente e prestador podem iniciar em `PENDING_PAYMENT` ou `CONFIRMED` (cliente com janela de 48h; prestador sem essa janela). Máximo **uma** solicitação **ativa** por `contracted_service_id`. | Feature `service-reschedule`; [ciclo-estados-reagendamento](./modulos/service-reschedule/features/ciclo-estados-reagendamento.md). |
| **Solicitação ativa (reagendamento)** | Linha aberta em `REQUESTED`, `PROPOSED` ou `ADJUSTMENT_REQUESTED`. Nova abertura com ativa existente → `ACTIVE_RESCHEDULE_EXISTS`. | Índice parcial; snapshot `activeRequest`. |
| **Rodada `SUPERSEDED`** | Estado terminal de rodada histórica: ao re-propor após `ADJUSTMENT_REQUESTED`, a linha atual vira `SUPERSEDED` e nasce nova linha `PROPOSED` com `parent_request_id` (cards imutáveis por mensagem). | FSM `service_reschedule_requests`; [ciclo-estados-reagendamento](./modulos/service-reschedule/features/ciclo-estados-reagendamento.md). |
| **Flags `can_*` (reagendamento)** | Flags de elegibilidade de UI no snapshot: `canClientRequestReschedule`, `canProviderRequestReschedule`, `canProposeReschedule`, `canAcceptReschedule`, `canRequestAdjustment`, `canCancelReschedule`. CTAs do card respeitam essas flags. | `ServiceRescheduleSnapshot`; `resolveRescheduleCardCtas`. |
| **Janitor expire (reagendamento)** | Job que move solicitações abertas para `EXPIRED` quando o slot proposto fica obsoleto (`proposed_slot.start_date ≤ cns_business_today`). Não envia MMD de cancelamento — só mensagem SYSTEM. Distinto do cancel por serviço `CANCELLED` (safety-net → `CANCELLED`). | Migration `service_reschedule_expiration_janitor`; constante `service_reschedule.batch_size`. |
| **Data proposta / Período proposto** | Rótulos de UI do slot enviado pelo prestador no reagendamento: data única vs intervalo com fim diferente do início. | `rescheduleCardCopy`, `ProposeRescheduleDialog`. |
| **Limiar de recaptura longe** | Dias após `paid_at` até a nova execução que separam reagendamento pós-`PAID` “perto” (mantém captura) de “longe” (reembolso + nova parcela T-2). Compara `payment_service_execution_at` com `paid_at + N` (não com `now()`), alinhado ao relógio de liquidação. Padrão **15**. | `platform_constants.far_reschedule_recapture_threshold_days`. |
| **Recaptura longe pós-`PAID`** | Após aceite de reagendamento com pagamento já capturado e nova data **além** do limiar: reembolso integral no gateway + nova parcela `SCHEDULED` em T-2; serviço → `PENDING_PAYMENT` até a nova captura. Não cancela serviço/chat. Orquestração backend (`process-far-reschedule-recapture` via pg_net + cron). | `payment_reschedule_charge_date`; EF `process-far-reschedule-recapture`; [integracao-pagamento-pos-aceite](./modulos/service-reschedule/features/integracao-pagamento-pos-aceite.md). |
| **Pendência de recaptura (`far_recapture_pending` / `farRecapturePending`)** | Flag no serviço contratado enquanto o reembolso+recaptura longe está em andamento (`far_recapture_pending_at` na parcela). UI mostra aviso discreto no detalhe (`ServiceModel.contracted`). | `project_service_row.far_recapture_pending`; `ServiceContractedSection`; view-services. |
| **`list_phase` / fase de produto** | Fase calculada no SQL (`derive_service_list_phase`): `negotiation` \| `in_progress` \| `completed` \| `cancelled`. Filtra abas de Meus Serviços; não reinventada no front. | RPC `list_services` / `get_service`; [visualizacao-de-servicos](./modulos/view-services/features/visualizacao-de-servicos.md). |
| **`ServiceModel`** | Contrato JSON único de lista e detalhe de pedido (`service_request_id`) para cliente e prestador (mapper `mapRpcServiceRow`). | Feature `view-services`; tipos em `view-services`. |
| **`serviceDetailPresentation`** | State de navegação: `"sheet"` + `background` abre detalhe em sheet sobre a lista; ausência (ex.: calendário, deep link) → página/stack cheia. | `serviceDetailNavigation.types.ts`; `ServiceDetailShell` / `DashboardLayout`. |
| **Taxa Renovi** | Constante de plataforma (`renovi_tax_provider`, ex. seed 0,15). Congelada na proposta (`tax_rate`, `final_amount`) e reutilizada no pagamento (`commission_rate_pct`, `provider_payout` em `payment_schedules`). | `platform_constants`, `provider_proposals`, `payment_schedules`. |
| **Valor base (`base_amount`)** | Preço do serviço acordado na proposta aceita (sem taxas de cartão). Base do split e das multas de cancelamento parciais. | `payment_schedules.base_amount`; checkout. |
| **Gross-up NetCred** | Fórmula do valor no cartão: `ROUND_HALF_EVEN((base_amount + PROCESSING + RISK_ANALYSIS) / (1 − MDR%/100), 2)`, para o líquido da plataforma ≈ comissão após taxas do gateway. Antecipação não entra (`automaticAdvance: false`). | `fee-calculator`; RPCs `payment_total_with_card_fees` / `payment_calculate_installment_options`; [checkout-e-cobranca](./modulos/payments/features/checkout-e-cobranca.md). |
| **Valor cobrado (`charge_amount`)** | Valor debitado no cartão do cliente, resultado do **gross-up NetCred**. O split do prestador (`provider_payout`) não muda com essa fórmula. | `payment_schedules.charge_amount`; seletor de parcelas. |
| **MDR (cartão)** | Percentual NetCred por bandeira e faixa de parcelas (constantes `cc_*_rate`). Usado no denominador do gross-up. | `platform_constants`; `payment_cc_fee_rate_key`. |
| **Taxa fixa PROCESSING** | Taxa fixa NetCred de processamento, em BRL (`cc_fixed_processing_fee_brl`; default prod R$ 0,39). Soma-se ao base antes do gross-up. | `platform_constants`. |
| **Taxa fixa RISK_ANALYSIS** | Taxa fixa NetCred de análise de risco, em BRL (`cc_risk_analysis_fee_brl`; default prod R$ 0,49; seed/sandbox local R$ 5,00). Soma-se ao base antes do gross-up. | `platform_constants`; `seed.sql`. |
| **T-2 (cobrança automática)** | Agenda de cobrança ≈ **execução − 2 dias** (`charge_scheduled_at`). Se no aceite faltam &lt; 48h, disclosure de emergência e a cobrança pode ser imediata. Cron `schedule-netcred-charges`. | [checkout-e-cobranca](./modulos/payments/features/checkout-e-cobranca.md). |
| **T-12h (auto-cancel)** | Janela `auto_cancel_hours_before_service` (default **12h**) antes da execução: cancela serviços com parcela `SCHEDULED`/`FAILED`/`FAILED_PERMANENT`/`IN_ANALYSIS` ainda não pagos; fecha chat; notifica MMD `SERVICE_AUTO_CANCELLED`. Distinto do cancelamento ToS. | `payment_auto_cancel_services`; [reconciliacao-e-voids](./modulos/payments/features/reconciliacao-e-voids.md). |
| **`IN_ANALYSIS`** | Parcela em análise antifraude/gateway pós-cobrança. Bloqueia cancelamento ToS (`PAYMENT_IN_ANALYSIS`); após T-12h entra no auto-cancel + void no gateway. | FSM `payment_schedules`; [checkout-e-cobranca](./modulos/payments/features/checkout-e-cobranca.md). |
| **`FAILED_PERMANENT`** | Estado terminal de falha de cobrança após esgotar tentativas. UI “Ajustar pagamento” (cobrança manual) até T-12h. | `payment_schedules`; `isManualPaymentEligible`. |
| **`VOIDED` vs `CANCELLED` (parcela)** | **`CANCELLED`**: auto-cancel T-12h ou pré-charge cancel (serviço cancelado); void pós-`IN_ANALYSIS` nesse path **permanece** `CANCELLED`. **`VOIDED`**: webhook `CHARGE_VOID` a partir de `PAID`/`IN_ANALYSIS`/`PROCESSING` — **não** é clawback de histórico (`refunded_at`). | [reconciliacao-e-voids](./modulos/payments/features/reconciliacao-e-voids.md); [historico-e-reembolso](./modulos/payments/features/historico-e-reembolso.md). |
| **`SERVICE_AUTO_CANCELLED` / `AUTO_CANCELLED`** | Código/evento de serviço cancelado automaticamente por falta de pagamento perto da execução (T-12h) ou tentativa de cobrança manual nessa janela. Template/notificação MMD; UI de cobrança manual pode mostrar view `service-cancelled`. | Edge/cron payments; MMD; [checkout-e-cobranca](./modulos/payments/features/checkout-e-cobranca.md). |
| **`deferred_captured`** | Outcome ops: gateway já `PAID` quando o domínio tenta void após auto-cancel — parcela permanece `CANCELLED`; warning; **sem** auto-refund neste path (risco: cliente cobrado com serviço cancelado no Orbit). | EF `reconcile-inanalysis-auto-cancel-voids`; [reconciliacao-e-voids](./modulos/payments/features/reconciliacao-e-voids.md). |
| **`DEAD_LETTER` (pagamentos)** | Evento de webhook NetCred com assinatura inválida / ingest unsigned → terminal sem retry que promova captura forjada. Reset operacional via `payment_reset_dead_letter_event`. *Não confundir* com `FAILED_TERMINAL` do MMD. | `netcred-webhook`; [reconciliacao-e-voids](./modulos/payments/features/reconciliacao-e-voids.md). |
| **Lease (cobrança)** | Trava (`locked_until` / SKIP LOCKED) para cron, cobrança manual ou reconcile não duplicarem charge na mesma parcela. Leftover `PROCESSING` tem política de orphan/lease. | `payment_claim_charge_batch`; `manual-charge-payment`; `PROCESSING_LEFTOVER_POLICY.md`. |
| **Platform company (NetCred)** | Company NetCred da **plataforma** Renovi (`NETCRED_PLATFORM_COMPANY_ID`): tokens de cartão são criados sob ela; cobrança/split usa a company do **prestador**. Mismatch → `PAYMENT_TOKEN_COMPANY_MISMATCH` (re-tokenizar). | Tokenização; Vault; [checkout-e-cobranca](./modulos/payments/features/checkout-e-cobranca.md). |
| **Código de falha (`failure_code`)** | Código estável Renovi gravado na parcela quando a cobrança falha. A UI de pagamento (alerta e dialog manual) mapeia esse código para mensagem amigável pt-BR — nunca o texto bruto do gateway. | `payment_schedules.failure_code`; `mapPaymentUserMessage`. |
| **Motivo de falha (`failure_reason`)** | Texto bruto retornado pelo gateway (ex.: `rejectedReason` NetCred/ClearSale), guardado para diagnóstico/suporte. **Não** é exibido ao cliente na UI. | `payment_schedules.failure_reason`. |
| **Rejeição por análise de risco (`RISK_ANALYSIS_*`)** | Quando `rejectedReason` da transação NetCred começa com “Análise de Risco: …”, o backend mapeia para códigos estáveis (`RISK_ANALYSIS_NO_CONTACT`, `…_FRAUD_SUSPICION`, `…_CANCELLED_DUPLICATE`, `…_CONFIRMED_FRAUD`, `…_BUSINESS_RULE`, `…_POLICY`, `…_MANUAL_FACILITATOR`, ou fallback `RISK_ANALYSIS_REJECTED`) e grava em `failure_code`. | `map-rejected-reason.ts`; cobrança T-2 e manual; [checkout-e-cobranca](./modulos/payments/features/checkout-e-cobranca.md#rejeição-por-análise-de-risco-clearsale--netcred). |
| **Repasse ao prestador (`provider_payout`)** | Valor fixo do prestador no split NetCred (`FIXED_AMOUNT`), congelado no aceite: `base_amount × (1 − commission_rate_pct/100)`. Não muda com a fórmula de `charge_amount`. | `payment_schedules.provider_payout`; ADR-0001. |
| **Histórico de captura vs Ganhos** | **Histórico (captura):** cobranças/recebimentos no cartão pós-`PAID` (cliente `client_payment_transactions_v`; prestador `provider_payment_receivables_v` com clawback só após `refunded_at`). **Ganhos:** depósito bancário previsto/efetivo (`payment_settlement_movements`) — distinto do valor na captura. | Features `payments` + `provider-earnings`; Minha conta / `/dashboard/earnings`. |
| **Histórico de pagamentos (cliente)** | Lista de cobranças no cartão pós-captura (`PAID` e estados de reembolso). Com `refunded_amount` > 0, a UI risca o valor original, mostra o líquido cobrado e a linha “Reembolsado: …”. | `client_payment_transactions_v`; `ClientPaymentHistoryList` em Minha conta. |

## Siglas

| Sigla | Significado |
|-------|-------------|
| **RLS** | Row Level Security — políticas de acesso por linha no Postgres (Supabase). |
| **RPC** | Função exposta no Postgres chamada pelo cliente ou Edge Function. |
| **FSM** | Finite State Machine — máquina de estados finita; usada no Message Dispatcher, pagamentos, reagendamento, etc. |
| **FCM** | Firebase Cloud Messaging — serviço do Google para envio de notificações push. |
| **BRT** | Horário de Brasília (America/Sao_Paulo); referência para janela de horário silencioso. |
| **JWT** | Token de sessão Supabase (uso em funções com `verify_jwt` ou validação manual). |
| **CEP** | Código de endereçamento postal — usado em fluxos de endereço. |
| **IA / LLM** | Modelos OpenAI ou Google Gemini conforme configuração da função de descrição inteligente. |
| **MMD** | Multichannel Message Dispatcher — ver **Message Dispatcher / MMD** na tabela principal. |
| **CNS** | Conversas e Negociação — ver entrada na tabela principal. |
| **H3** | Sistema de indexação espacial hexagonal (Uber H3); na Renovi, resolução **7** no matching/beacon. |
| **ToS** | Termos / política de cancelamento com faixas de estorno (`FULL_REFUND`, `PENALTY_10`, `PENALTY_30`, `PROVIDER_FULL_REFUND`). |
| **ClearSale** | Antifraude / análise de risco via NetCred. Sessão emitida pelo servidor; em produção o checkout/cron falha fechado sem sessão. Motivos “Análise de Risco: …” viram códigos `RISK_ANALYSIS_*`. |
| **Sessão ClearSale** | UUID antifraude emitido por `payment_issue_clearsale_session`, vinculado a usuário+proposta ou parcela; consumido na cobrança T-2 e manual. |
| **Token de cartão (company-bound) / platform company** | `client_card_tokens` ligados à company NetCred da **plataforma** Renovi (`NETCRED_PLATFORM_COMPANY_ID`); mismatch com Vault exige re-tokenizar. Cobrança usa company do prestador. |

## Nomenclaturas que podem confundir

| UI (menu) / termo | Código / conceito |
|-------------------|-------------------|
| “Meus Serviços” (cliente) | Lista de **pedidos** (`service_requests`), não serviços ofertados. |
| “Meus Serviços” (prestador) | Também pedidos, vistos como oportunidades de trabalho (não o feed geográfico de Trabalhos). |
| “Orçamentos” | **Prestador:** negociação em **Conversas**; pedidos em que participa via **Meus Serviços** (`view-services`). **Cliente:** comparar/histórico no card em **Meus Serviços**; negociação em **Conversas**. |
| “Dispatch” (duas acepções) | **Message Dispatcher / MMD:** fila de e-mail/push. **Matching:** `service_request_dispatches` — lotes e gates do pedido. |
| “Histórico de pagamentos” vs “Ganhos” | Captura no cartão / líquido pós-clawback ≠ depósito bancário (settlement movements). |
| “`CANCELLED`” vs “`VOIDED`” (parcela) | Auto-cancel/pré-charge → `CANCELLED`; webhook void de captura → `VOIDED` (sem `refunded_at`). |
| “`DEAD_LETTER`” (pagamentos) vs `FAILED_TERMINAL` (MMD) | Webhook NetCred inválido vs falha terminal de envio de mensagem. |
| “Lease” (três acepções) | Matching (lote), cobrança NetCred (parcela), MMD worker (`PROCESSING`). |
| “Cooldown” (duas acepções) | Soft prompt push: **7 dias** após dismiss. MMD push: **1 min** entre envios (stagger). |
| GPS do feed vs beacon | Sort “Mais próximos” usa GPS foreground; elegibilidade de **lote** usa beacon / `provider_latest_locations` + freshness. |
| Calendário vs Meus Serviços | Calendário = agenda temporal somente leitura; Meus Serviços = lista filtrada por fase/`list_phase`. |
